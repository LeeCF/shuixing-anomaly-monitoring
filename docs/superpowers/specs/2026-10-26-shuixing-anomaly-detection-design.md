# 水星家纺 异常交易实施监测 — PoC 设计规格

**项目：** TGD 2026 GC Hackathon — 水星家纺 AI 异常交易监测  
**日期：** 2026-10-26  
**PoC 窗口：** 1 天（模拟交互界面，无需真实检测引擎）  
**核心卖点：** AI 告警卡（原因 + 历史案例 + 建议动作）+ Fiori 风 Web 展示  

---

## 1. 目标与范围

### 客户来源与定位

本项目对应客户《水星家纺AI场景_财务》10 场景清单中的 **场景 5「异常交易实时检测」**（风控层）。客户原文要求：三层一起跑（规则 + 统计异常 + 行为画像），输出"异常原因 + 相似历史案例 + 建议动作"，而非"判定异常"四个字。该场景是枢纽——清单中场景 7（合规审查）、场景 9（成本差异分析）均标注"跟场景 5 相通"，做出彩可放大演示价值。

三个 demo 场景均取自客户明确点名的覆盖范围（供应商付款 / 重复付款 / 拆单·临界值行为），刻意各打一层：

| # | 场景 | 主打层 | 客户点名 |
|---|------|--------|---------|
| 1 | 供应商银行账户变更后首笔大额付款 | 画像/行为层 | 供应商付款 |
| 2 | 重复付款 | 规则层 | 重复付款 |
| 3 | 临界值聚集拆单 | 统计+画像层 | 拆单 / 临界值行为 |

### 目标

用一个可演示的 PoC 证明：**AI 不只是"判定异常"，而是给出可执行的决策支持**——异常原因（三层联动）+ 相似历史案例（RAG）+ 建议动作，全部输出为结构化告警卡，展示在 Fiori 风格页面上。

### PoC 范围（严格限定）

- **包含：** 3 张预制告警卡（逼真 JSON 硬编码）+ Fiori 风格交互 Web UI + 模拟检测触发动画
- **不包含：** 真实检测算法、真实 LLM 调用、ERP 接入、生产级权限  
- **架构设计仍预留接缝**：向评委解释"换成真实引擎只需替换数据源和 LLM 适配器"

### 成功标准

演示时能完成以下流程：  
1. 打开列表页，看到 3 条不同类型的告警  
2. 点进某条，看到完整 6 要素告警卡（含 AI 生成的原因分析、Top3 相似案例、建议动作）  
3. 回答评委"这个 Z-score / 集中度评分哪来的"——全部真算，能解释

## 2. 架构

```
┌─────────────────────────────────────────────────────────┐
│  数据层                                                   │
│  SQLite: transactions / vendors / employees / alerts     │
│  鼎捷ERP桩 (可替换适配器, 当前=SQLite 直连)               │
└────────────────────┬────────────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────────────┐
│  检测层（Python, 三层）                                   │
│  · 规则层: SQL 查询（职责分离/账户变更/三单不匹配）         │
│  · 统计层: numpy Z-score（历史频次/金额分布）              │
│  · 画像层: 集中度评分（员工-供应商交易占比）               │
└────────────────────┬────────────────────────────────────┘
                     │ AnomalySignal(rule, stat, profile)
┌────────────────────▼────────────────────────────────────┐
│  RAG 层: 历史案例检索 Top3                                │
│  · 本地兜底: TF-IDF 关键词匹配（stdlib+json）             │
│  · 可替换: HANA Cloud 向量引擎 / 任意向量库               │
└────────────────────┬────────────────────────────────────┘
                     │ SimilarCase[]
┌────────────────────▼────────────────────────────────────┐
│  AI 层: 告警卡生成                                        │
│  · 本地兜底: 结构化模板填充（无 LLM 依赖）                │
│  · 可替换: SAP AI Core + Qwen / Generative AI Hub        │
│  输出: AlertCard JSON（6 要素）                           │
└────────────────────┬────────────────────────────────────┘
                     │ AlertCard JSON
┌────────────────────▼────────────────────────────────────┐
│  Web UI (Fiori 风格)                                     │
│  · 告警列表页: 编号/风险分/级别/摘要                      │
│  · 告警详情页: 完整 6 要素卡                              │
│  技术: 纯 HTML/JS + SAP Fundamental Styles CSS           │
│  由 FastAPI 静态托管, 无独立前端构建                      │
└─────────────────────────────────────────────────────────┘
```

### 三处可替换适配器

| 适配器 | 本地兜底实现 | 目标环境实现 |
|--------|------------|------------|
| ERP 数据源 | SQLite（造数） | 鼎捷 ERP → BTP 集成层 |
| 历史案例检索 | TF-IDF 关键词匹配 | HANA Cloud 向量引擎 |
| LLM | 结构化模板 | AI Core + Qwen / Generative AI Hub |

配置切换：单一 `config.yaml`，改一行即可切换任意适配器。

## 3. 技术栈

| 层 | 技术 | 理由 |
|----|------|------|
| 后端 | Python 3.11 + FastAPI | AI Core SDK 是 Python；numpy 统计顺手；单进程托管 API + 静态页 |
| 数据 | SQLite（stdlib） | 零部署，造数/历史/案例库一文件 |
| 前端 | HTML/JS + SAP Fundamental Styles | 官方 Fiori Horizon CSS，无构建工程 |
| 统计 | numpy | Z-score 一行，无额外依赖 |
| LLM 兜底 | Python f-string 模板 | 环境未到时保证演示完整 |
| RAG 兜底 | sklearn TF-IDF 或手写余弦 | 确保 Top3 案例检索可演示 |

**刻意跳过：** Docker、前端构建工具（Vite/webpack）、消息队列、CAP/OData、独立数据库服务。

## 4. 数据设计

### 4.1 数据库表（SQLite）

```sql
transactions   -- 交易流水: id, date, amount, employee_id, vendor_id, 
               --          po_number, invoice_number, created_by, approved_by,
               --          created_at (timestamp)
employees      -- 员工: id, name, dept, role
vendors        -- 供应商: id, name, created_at, bank_account, bank_changed_at,
               --         has_purchase_history, has_receipt_history
historical_cases -- 历史已确认案例: id, type, description, amount, outcome, date
alerts         -- 生成的告警卡: id, alert_no, risk_score, level, card_json, created_at
```

### 4.2 三个 Demo 场景的数据埋法

每个场景：先生成 6-12 个月"正常历史"，再埋入异常——确保三层信号全是真算出来的。

---

**场景 1：供应商银行账户变更后首笔大额付款（画像/行为层主打）**

> 商业邮件诈骗（BEC）最典型模式：攻击者伪冒供应商提交换账信息，新账户首笔就是大额。

- 供应商"S001-XX纺织材料" 有 18 个月正常交易历史
- 在 T-3 天发生银行账户变更（bank_changed_at 字段）
- T 日发生一笔 42 万元付款（历史单笔均值 8 万）
- **三层信号：**
  - 规则层：付款发生在账户变更后 72 小时内
  - 统计层：金额 Z-score = (42-8)/σ，σ 由历史数据真算
  - 画像层：账户变更→首笔付款间隔评分（越短越危险）

---

**场景 2：重复付款（规则层主打）**

> 客户明确点名场景。多套系统孤岛下最易发生：同一笔应付被不同系统/不同经办各付一次。

- 供应商"S002-XX印染" 有正常交易历史
- 存在一笔原始付款：2026-10-10，金额 23.6 万，发票号 INV-2026-8842
- T 日（2026-10-22）又出现一笔：同供应商 + 同金额 23.6 万 + 同发票号 INV-2026-8842，经办人不同
- **三层信号：**
  - 规则层：同供应商 + 同金额 + 同发票号，30 天内出现 ≥2 次，硬命中
  - 统计层：该发票号重复计数 = 2（正常应为 1）；两笔间隔 12 天
  - 画像层：两笔分属不同经办人/不同渠道（跨系统孤岛特征）

---

**场景 3：临界值聚集拆单（统计 + 画像层主打）**

> 员工长期把金额压在审批阈值正下方——本福特定律的典型体现。

- 审批阈值设定为 5 万元
- 员工"E003-王某"过去 6 个月记录：随机分布 1 万-8 万，无明显规律
- 最近 90 天：15 笔付款，13 笔落在 4.7 万-4.98 万区间
- **三层信号：**
  - 规则层：90天内 ≥10 笔落在阈值 ±5% 区间（软触发）
  - 统计层：阈值区间命中率 vs. 历史均值，Z-score 真算；使用滑动窗口检测聚集时间段
  - 画像层：E003 阈值下方累计金额 / 总付款额占比（集中度偏差）

---

### 4.3 历史案例库（RAG 检索用）

预置 8-10 条已确认处置案例，覆盖三个场景类型，含字段：  
`类型 / 描述 / 金额区间 / 处置结果 / 教训摘要`

检索策略（兜底）：场景类型精确匹配 → 金额区间相近 → 关键词余弦相似度，取 Top3。

## 6. API 设计

| 端点 | 方法 | 描述 |
|------|------|------|
| `/api/alerts` | GET | 告警列表（分页，含 risk_score/level/摘要） |
| `/api/alerts/{id}` | GET | 单条告警完整卡 JSON |
| `/api/detect/run` | POST | 手动触发检测（demo 用，对 SQLite 造数跑一遍） |
| `/` | GET | 静态页面入口 |

## 7. UI 页面规格

### 7.1 告警列表页

- Fiori 表格：列 = 告警编号 / 风险评分（色标：红≥80/橙60-79/黄40-59）/ 级别 / 场景类型 / 涉及方 / 时间
- 顶部过滤栏：级别 / 场景类型 / 时间范围
- 点击行跳转详情

### 7.2 告警详情页（卡片页）

- 头部：编号 + 风险评分大字 + 级别徽章
- ① 异常描述区块
- ② 三层联动原因（规则/统计/画像 三个 Fiori InfoTile 并排）
- ③ 相似历史案例（Top3，Fiori List 样式）
- ④ 建议动作（按紧急程度分组，【立即】红色，【24h内】橙色，【可选】灰色）
- ⑤ 涉及方标签行
- ⑥ 数据溯源面包屑
